## Architectural verdict

The specification's shared-engine direction is sound. Its statement that the existing backend already accommodates web/PDF/API sources does not establish that the current domain supports numeric or transient states. The current domain remains coupled to legal documents and legal events in SQL CHECK constraints, foreign keys, connectors, materiality code, briefs and feed projections. Merely adding ten templates over `MonitoringTopic` would leave core requirements unsatisfied and risks presenting a train delay as a regulatory amendment.

Keep the current modular monolith and single-host deployment. Add a small generic monitoring domain inside the same FastAPI/PostgreSQL/Celery stack, with a compatibility projection from the existing regulatory corpus. Reuse existing security, durable jobs, artifact storage, source packs, UI components, queues and observability. Preserve the existing legal engine as a supported legacy domain; do not rebuild legal comparison or force telemetry through legal-unit parsing. New generic objects are domain contracts; not every noun needs a new table or service.

The ten new use cases are mandatory final scope. They may be enabled by verified template/source pack in staged releases. A staged release containing five templates is not completion of Monitoring v2, and an implemented template with no verified usable source is not an available capability.

## Minimal shared domain contract to freeze before parallel build

1. **Workspace/owner:** existing Organization boundary plus explicit personal workspace metadata; each Subject has one owner workspace, creator and optional assigned owner. A personal workspace is owned by its user and is not inherited by company members. B2C settings can be edited by their owner; business viewer cannot mutate organization monitoring. Any personal monitor within a shared workspace would require an additional principal authorization predicate on every read/write/export/job; avoid that complexity for the first cut.
2. **MonitoringSubject + immutable configuration revision:** template ID/version, typed scope/filters/thresholds/rule revision, source pack references, paused/active/archived, notification settings, explicit idempotency key. Revision comparison uses CAS; preview must run the exact matcher/rules that activation will use. Show source unavailable/partial before save, never silently change canton, station or scope. User can save a paused draft for an unavailable template but cannot be told it is actively monitoring.
3. **ObservedEntity:** shared authoritative object identity, domain/type, authority, upstream key and entity instance. Separate aliases/editions/attachments with evidence-backed identity linking. Do not merge two same-title tenders, different trip service days, opposite-direction road incidents, different stations or Nice-class variants solely using fuzzy title.
4. **ObservedState:** immutable normalized payload with schema/adapter version, raw evidence references, source status, quality, metric/unit/precision as applicable and distinct event/effective/source measurement/detected/fetched timestamps. Preserve time precision and uncertainty. Use UTC instants plus IANA Europe/Zurich schedule semantics, DST-safe half-open windows, and source civil date when only a day is known. Incompleteness is not zero and absence from a partial poll is not cancellation.
5. **ChangeSet:** previous/current state references, typed changes, deterministic materiality rule/version, facts used and evaluated thresholds. Publication, content, geography, instruction, numeric, attachment and deadline changes are separate from metadata refresh/noise. Preserve nonmaterial auditability without generating user notifications for every refresh.
6. **Development:** stable user-facing real-world story with many immutable changes, source records and language editions. Source lifecycle (active/escalated/downgraded/cancelled/resolved/expired) is separate from ingestion pipeline lifecycle and review lifecycle. Current pointer changes through atomic versioned transactions. Cross-source uncertain cluster candidates stay separate until justified; support audited split/merge correction without erasing delivery/decision history.
7. **RelevanceAssessment:** workspace/subject-revision/development-change binding, relevant, method, structured reason, supporting facts, optional score and model provenance. Facts include intersecting municipality/geometry, trip/stop/window, threshold baseline, profile criteria and exclusion decisions. Store negative outcomes sufficiently for missed-item audit. Relevance configuration edits trigger bounded reevaluation; they do not rewrite historical reasons or automatically spam old results.
8. **Review/Decision:** append-only scoped reviewer/actor/time/version/decision/comment/owner and decision snapshot. Shared business decision is distinct from private opened/read/mute; no new inference required. Support common decisions plus BID/NO_BID/INSPECT/ESCALATE_TO_IP_COUNSEL. A material update invalidates the reviewed-through revision and yields REOPENED; it retains the earlier review and assigned owner. Cancellation closes the active source development even when no user has opened it; historical decisions remain inspectable.
9. **NotificationRule/Delivery binding:** existing queue/outbox and preferences extended with channel, priority, quiet hours, thresholds, cooldown/aggregation, temporary pause, event mute vs hazard-type/subject mute, eligibility and expiration. Deterministic key includes recipient/workspace/development/material-change-or-reminder/policy/channel; multi-subject matches list all reasons once. Preserve receipt ledger across retries, reconnects, backfills and migration. Separate platform operational notice from domain development. Explicit opt-in is required before high-priority quiet-hour bypass; source failure must never send an all-clear.
10. **Deadline:** typed source-stated or calculated timestamp/date, evidence, precision/timezone, rule/version, owner and status. Calculated dates show inputs and verification state; unknown date is not guessed. Reminder idempotency is tied to current deadline revision; moving/cancelling a deadline cancels stale scheduled reminders. User-dependent legal deadline calculation must not be portrayed as an authoritative fact.

## Cross-case edge cases the backlog should name

- New entity baseline versus truly new event: existing official tender seen during initial history import should say newly discovered, not just published. Historic expired hazards must never emit live urgency. Subject activation uses explicit bounded baseline/backfill policy.
- Clock skew, duplicate source revision, out-of-order updates, backdated corrections, station gaps, missing values, equal threshold boundary, negative/zero baselines, floating point precision, measurement-unit changes and source format drift need deterministic handling. Old observation must not overwrite a newer state merely because it arrived later.
- Threshold crossing alone is insufficient: define baseline (previous observation/previous day/user reference), direction, percent denominator, absolute units, inclusive comparison, cooldown, reset and hysteresis per template. This is shared machinery with different domain defaults.
- Hazard geography changes can be relevant even if severity is unchanged. If an affected area shrinks past a watched location, issue its relevant downgrade/no-longer-affected update. Preserve official instructions without personalized emergency reinterpretation.
- C2 time windows cross midnight/DST and service dates; route/line identifiers differ. C3 direction and official segment geometry matter. A road-name string match is not route intersection. Resumption/expiry differs from source outage.
- C5–C7 measured values, forecasts, categories and official warning levels are distinct. Nearest station does not automatically represent an arbitrary municipality; store distance/coverage and user-visible limits.
- C4 official customs exchange rate is not a live trading/retail FX rate. Preserve validity date, currency pair, unit multiplier and exact rounding. A user's threshold may need previous valid business day/reference rather than last poll.
- B2 publication/lot/update/Q&A/attachment/deadline identity is one procurement story with subobjects. B7 similar-name candidate is not infringement; exact vs fuzzy vs phonetic score must be explained and class/services overlap retained. B8 auction listing and current price/bid/status/deadline are distinct; unsupported live bidding fields stay explicitly unavailable and cannot masquerade as zero.
- C1 severe source instructions and C2 imminent cancellation must still display and deliver correctly when local AI is offline. AI failure can downgrade confidence in an explanation, not invalidate an authoritative instruction or fabricate a no-change result.
- Shared public corpus should not record private home coordinates in global evidence or analytics. Matching belongs inside the owning workspace. Brand/business profiles, home/commute, review notes and custom financial reference values follow the existing tenant/privacy boundary.
- Retention must account for telemetry volume. Every delivered change's evidence and review history remain preserved. Unchanged high-frequency raw polls can have explicit bounded retention/deduplication, while published normalized state history/citable snapshots obey the disclosed policy. Do not promise infinite storage of every upstream message or delete previously saved MVP evidence.

## Compatibility and rollout plan

**Step 0 — baseline and contracts.** Pin the current MVP tag/commit and record routes, ids, artifacts, histories, subscriptions, personal state and Basel journey fixtures. Freeze the generic schemas and enums, privacy model, notification identity, source health meaning and per-template configuration. Obtain source feasibility evidence early, before dependent UI claims. Write migration manifest/read compatibility contract, not a rewrite.

**Step 1 — additive schema.** Introduce generic tables/projections without renaming/removing `laws`, `versions`, `regulatory_*`, `DocumentWatch`, `MonitoringTopic`, old API fields or object ids. Register new private models in tenant scopes and shared models in shared-corpus policy. New tables have restrictive constraints/indexes/idempotency and versions; record migration/rollback bounds. Existing enum limitations remain explicit and legal UI sees only legal objects.

**Step 2 — bridge existing legal corpus.** Use stable unique bindings from legacy watch/topic/event/version to subject/entity/state/development. Legal authoritative write remains in existing ingestion; generic projection updates transactionally or via the existing outbox with a durable backfill cursor. Do not maintain two independently editable copies of the same legal state. Preserve legacy evidence links, versions, comparisons, analysis reports, active pack choices, review histories and private states. Coalescing multiple old events needs an explicit deterministic grouping key; do not reset viewed states or silently combine unrelated decisions.

**Step 3 — notification suppression during migration.** Replayed/backfilled events create baseline/history under a migration admission cutoff and migration generation. They cannot re-send already delivered items; maintain old event delivery bindings as aliases. New material changes after the cutoff can reopen a review once. Preview of migration reports counts, duplicates, unmatched mappings, stale/source status, authorization and evidence checks before enabling notifications.

**Step 4 — shadow comparison.** Run new projection/matcher beside legacy readers for saved seeded corpus and representative real source artifacts. Compare subject/event counts, evidence hashes, authorization, unread/mute state, deep links, paging and digest inclusion. A discrepancy is reviewable and bounded; do not silently use majority/approximation. Features can be disabled by template/workspace while deterministic MVP paths keep working.

**Step 5 — incremental enablement.** Bring one real end-to-end subject (C4 numeric is a useful low-risk implementation proving state/threshold/evidence/review) and one event lifecycle (C1) through common engine, then other environment, mobility and business templates. Freeze final scope of ten; source-feasibility results can adjust order and exact coverage, not erase a requested capability. Regulatory/Basel journeys remain supported alongside generic Today.

**Step 6 — upgrade/recovery acceptance.** On an isolated clone of representative persisted data rehearse upgrade, interruption/resume, app rollback with additive schema and full restore if needed. Verify old/new jobs cannot consume incompatible contract versions and no irreversible production downgrade is attempted. Actual production migration/deployment is separate execution authorization from backlog publication. Complete source, target hardware, localization and human-pilot gates before expanding claims/public registration.
